# Window Use MCP

Status: implemented for Windows x64. The independent package, permission UI, real UI Automation and physical-coordinate input, self-protection and lifecycle checks are verified on the current Windows desktop. Clean-machine and individual third-party client acceptance remain unverified. Execution evidence belongs in the work record.

## Product boundary

The MCP initialize server identity is `az_window_use`. Default client examples use the same registration key; the client key determines callable namespaces. Azrael reserves that key for its built-in server and preserves a conflicting external registration under the first free numbered alias. Other clients must configure unique connection keys; equal `serverInfo.name` values do not merge servers or grant shared authority.

An independent Windows x64 interactive-desktop MCP server ships with its native window-control engine, cooperative input broker and Electron runtime. MCP clients launch the executable with `--mcp` using stdio. Launching it without that flag opens settings. Azrael, VS Code and a separately installed Node runtime are not required. No network listener is exposed.

A console launcher owns Windows standard input/output and relays messages through a random current-user named pipe to the GUI host. The host authenticates with a one-time random token before any protocol bytes are forwarded. The pipe does not grant app authority. Electron's GUI process does not own public stdio. The launcher removes inherited Node-mode environment settings, and the packaged host disables RunAsNode. EOF closes the pipe, cancels pending approvals and releases owned input.

## Permission owner

The main process owns settings, connection identities and grants. MCP arguments and client-provided names never grant authority. Each process assigns a random connection identity; temporary grants apply only to that connection. App approvals name the exact normalized executable and permission. Desktop control expires on disconnect or process exit. Denial, expiry, Stop and changed policy cancel waiting approvals and invalidate observations. No unknown input is replayed.

The enabled switch gates managed operations. Observation mode denies mutations. Ask mode requests app control permission on first use; full mode skips those prompts but retains protected apps, target checks and Stop. App observation is allowed while enabled except protected apps. Protected apps remain unobservable and uncontrollable, with masking for whole-desktop captures. Settings permit user-managed protected and permanently allowed apps. Permission requests automatically open a compact approval window; only trusted local UI actions can answer them.

## UI and self-protection

A frameless compact settings window and tray expose enable/mode, protected apps, saved grants and Stop. Approval windows state the app, executable, requested scope and expiry. Light/dark themes reuse Azrael's semantic colors, settings rows and permission labels. The window retains an application drag region and accessible close/minimize controls.

The MCP launcher starts its UI-capable host automatically; users need not start a separate settings application. MCP mode initially has no settings or approval renderer. A permission request creates and shows the approval window on demand, or restores its existing window. Closing a window releases that renderer while the MCP host and tray remain available. Closing an approval denies its pending requests; a subsequent independent request creates a new approval window. A request cancelled during window loading must not surface an obsolete approval. Explicit tray Quit and MCP disconnect terminate the host; they do not silently restart or replay pending input. Host-client tool approvals occur before MCP dispatch and remain the client's responsibility.

Every own executable identity is an immutable entry in the same protected-app list passed to native masking and checked before semantic or coordinate input. Own settings and approval windows cannot be unblocked, observed or controlled through this MCP, including in full mode. The preload exposes only named operations, authenticates the exact top-frame sender and validates arguments in main. Node integration and remote content are disabled. UI permissions are server guardrails, not OS isolation from other programs running as the same user.

## Reused execution

Concurrent native cursor overlays use locale-independent `Agent N` labels and distinct reserved colors across participating MCP processes in the same Windows logon session. A white physical cursor is labelled `User`. Windows named-object handles retain the lowest free number and a color through exit fading, and release on destruction or process termination. Automatic colors reuse the 72 registered palette entries (different hue families first); exhaustion or an explicitly requested color already in use fails instead of duplicating. Numbers may be reused after release and grant no authority. Older running binaries must reconnect to participate.

Control overlays remain recordable (`WDA_NONE`, without capture-exclusion flags) for compatibility with desktop recorders. Borders, status text and Stop UI may appear in recordings. This does not remove MCP protected-app masking or control restrictions; external recording software has its own capture policy.

Pinned Azrael policy and native sources retain exact window lifetime identities, stale-observation rejection, bounded UI Automation queries, password withholding, window occupancy, masked desktop capture and cooperative physical input rules. A standalone adapter supplies settings, approvals, connection context and input callbacks without fabricating Codex metadata. Native executables and payloads are verified from content manifests before launch.

Real switched/desktop input sessions request virtualized collaboration by default on their first operation. Replacement sessions repeat this initialization under the existing permission and cancellation guards. An explicit collaboration disable applies until that session ends. Cosmetic-only pointer visualization does not enable interception. Device snapshot, Raw Input registration, replacement user cursor and guard initialize synchronously; success returns ready without any physical input. Awaiting-motion and suppressed-Raw startup probing are removed. Initialization readiness does not claim that physical Raw Input survival has already been proven; actual device/origin/delivery/hook checks remain at runtime. During virtualized mouse work, physical keyboard events remain observable without cancelling mouse routing or advancing its interruption epoch. Cooperative mouse and model key/text operations use the bounded keyboard reservation below; foreign injection, emergency Stop, disconnect and target validation remain active. Explicitly disabled collaboration keeps shared Windows modifier semantics.

### Public pointer coordinates and gestures

`switched_input` uses integer pixels of the PNG returned by `capture` with the exact fresh observationId: top-left (0,0), exclusive width/height bounds. `coordinateSpace` returns image dimensions, physical `screenBounds`, and scaleX/scaleY. Windows WGC pixels must exactly match DWM extended frame bounds; this implementation does not resize images, so scale is 1. Native capture rejects uncertain mappings or movement during capture. The host binds geometry to the observation and rechecks origin, dimensions and DPI through input guards. Out-of-image coordinates or changed geometry reject before dispatch; a change after dispatch is uncertain and must not be replayed. Input remains restricted to the verified app surface, so an image's non-client pixels are not automatically valid input targets.

`desktop_input` retains absolute physical screen pixels (including negative origins) and its independent desktop capture/permission checks. Both public tools take `points:[[x,y],...]` without an action for pointer gestures: one point clicks (left by default; right/middle supported), two points drag straight, 3..32 follow centripetal Catmull-Rom. All points include explicit start/end. durationMs is total drag time, 50..2000ms (default 300), and is rejected for clicks. All-identical multi-point paths fail before input. Public move/click/drag actions and x/y/fromX/fromY forms are retired; native broker wire actions stay explicit. Scroll/press/text/batch remain explicit actions with one location point, as do optional batch click locations. Status/collaboration need no location for selected-window sessions; desktop calls require one location to resolve their target. Sparse curve anchors and short dependent batch sequences are described in context and tool guidance. Selection among external tools is left to the client. Within Window Use, guidance prefers bounded UIA inspection for text, values and states, and supported semantic element actions for controls; capture and pointer input serve visual judgment and spatial interaction. Known task macros resolve explicit selectors afresh at each step, reducing model round trips rather than UIA queries. Capture defaults to image-only (includeUIA:false). With includeUIA:true it also retrieves a bounded UIA summary (up to 20 elements) and retains image geometry and element references under one observationId, usable for either semantic control or pointer input. Pixels and UIA are sampled sequentially, not atomically; identity and geometry are revalidated after collection, and UIA retrieval errors fail the combined call without silently falling back to image-only. Retrieval coverage and truncation are returned. Separate capture/inspect calls still replace the current observation, so inspect cannot preserve an earlier image observation for pointer input. Any mutation still consumes the observation. The context guide is the sole location for window occupancy instructions; individual tool descriptions retain their purpose, coordinate rules and state fields. Retired pointer syntax is not enumerated in model-facing guidance.

### Curved drag

After public coordinate validation/conversion, the adapter sends native `drag` with 2..32 physical integer screen-pixel anchors including the explicit start and end. Desktop observation checks every anchor, and target resolution/pointer creation use the first point. Native code removes consecutive duplicates (all-identical paths fail), uses centripetal Catmull-Rom alpha 0.5 with reflected endpoint neighbors, converts each piece to cubic Bezier and adaptively flattens it with a 0.25px control-hull chord bound. Approximate arc-length resampling includes every anchor, <=2px geometric travel and <=10ms intended cadence, capped at 2048 delivery samples. Duration remains 50..2000ms (default 300ms); OS scheduling and per-event delivery can overrun it. No sample trace is returned in normal responses.

Before focus preparation or button-down, every generated rounded delivery pixel must be in the pinned target and virtual screen. Runtime identity, hit-testing, shared physical modifier semantics, Stop/disconnect, known-held-button cleanup and operation no-replay rules remain. One call presses once, follows the whole path and releases once. Geometry approximation, integer rounding, delivered OS input and application-rendered strokes are distinct; input acceptance does not prove application effect. This is not an obstacle planner or a pen/pressure API; cooperative drags use the keyboard reservation below. Paths exceeding the bounded sample capacity fail before input rather than being silently simplified.

### Reserved keyboard input and batches

On Windows x64, cooperative click/drag/scroll, `press`/`text` and `batch` reserve the keyboard before target activation. Click/scroll budgets are 1000ms; drag budgets are durationMs + 1000ms (maximum 3000ms). Validation precedes reservation. Batch steps share the existing outer deadline and restore once at the end. A batch has 1–16 click/text/press steps, one pointer/target and operation ID, a default 750ms budget (100–1000ms), and at most 1024 UTF-16 text units. Native code validates every step and coordinate before reserving input; the FIFO executes without another human gesture or model move between steps. This provides ordered input, not application rollback or verified application effects.

Physical key edges enter a preallocated 4096-event buffer without advancing the model interruption epoch. Initially held keys are temporarily neutralized. On completion, native code revalidates the original process/root/focused child, restores foreground/focus, reconstructs initial held state, and inserts buffered edges in order. Consumed records are zeroized. The existing user-cursor waiting presentation remains active during reservation. Foreign injection, Stop/disconnect, target invalidation and the emergency chord still abort model work. Completion cleanup allows 50ms for pending model input dispatch before restoration, with the hook still pumping and buffering. This is bounded settling, not an application acknowledgment. Restoration pins Windows HWND focus; it does not separately snapshot DOM elements, selection or IME composition.

Each chord/text uses one SendInput insertion instead of per-character UI round trips. Before keyboard delivery, native code waits up to 100ms for an allowed foreground/focus and pins that focus through the packet. This validates an allowed window surface, not the semantic identity of a clicked element. Unicode text does not virtualize IME composition. Results expose only batch progress and keyboard counts/restoration/failure categories; key contents are not logged. A duplicate or uncertain operation is never replayed; delivery counts describe Windows insertion, not app consumption.

The timer/high-water mark requests abort; focus restoration/replay waits for synchronized broker cleanup to avoid racing model injection. An independent input-safety process is armed before keyboard or mouse suppression. It consumes only physical Esc (down, repeat and matching up), requests cancellation, and enforces a non-extendable 10-second ceiling over overlapping suppression gates. Existing 750/1000/3000ms budgets remain unchanged. A missing UI heartbeat requests cancellation after 1500ms; cancellation gives synchronized cleanup 250ms, within the hard ceiling. If suppression remains, the guard terminates only the exact inherited native-helper process and waits for exit before releasing model-owned keys/buttons from its shared ledger. Guardian hooks track physical key/button edges and protect a newly held physical key/button from own-tag recovery releases at hook delivery. This removes that process's hooks; the separate cursor guard restores visibility. Forced recovery cannot restore the lost in-memory user buffer or guarantee original focus; delivery is unknown and is never replayed. The guard reports recovery on stderr and the failed operation requires a new observation. A stopped or missing guard prevents new suppression. High-water abort begins at 3072 events; actual overflow reports unresolved failure and cannot reconstruct lost edges. Destroyed original windows, denied restoration, uncertain insertion or user shortcuts changing focus during replay can leave pending input; it is never blindly redirected. Real physical-hook concurrency, IME and remapping/Raw Input consumers require real-device acceptance. Mouse startup requires no user-input event or suppression probe.

## Data and failures

Settings live under the product's own user-data directory and are revision-checked and atomically persisted. Corrupt settings fail closed. Logs record lifecycle, request names, correlation IDs, outcome and duration without screenshot data, UI text, typed text or credentials. Logs are bounded. Runtime failure, failed IPC or missing UI never creates a grant. Disconnect releases owned input and pending requests without closing user applications.
